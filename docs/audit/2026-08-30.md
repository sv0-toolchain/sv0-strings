## Evidence boundaries (SPEC §4.7, GOV-013)

- **`sv0-mathlib` `v0.1.0` is not transitive proof.** Its tag, its R1
  self-classification, and its passing suite are evidence about *that*
  repository's accepted scope only. They do **not** close any `sv0-strings`
  requirement. In particular sv0-mathlib exercises no byte slices, embedded
  NULs, mutable buffers, borrow enforcement, allocation failure, destruction,
  or C/POSIX compatibility semantics.
- **Reusable patterns** (not evidence): its generated requirement matrix,
  deterministic seeded property program, fixture manifest + provenance checker,
  documentation-coverage lint, and package-owned `scripts/ci`. `sv0-strings`
  SHOULD adopt the same shapes (see `tools/` slices `SS-002`..`SS-004`).
- **Its documented workarounds are not capability proof.** Concrete
  `OptionI64`/`OptionF64`-style carriers, free-function operators, struct-return
  substitutions, filename staging, and field-to-local rewrites are evidence that
  the underlying generic / trait / tuple / struct-payload / project-order /
  field-lowering capabilities are **absent**, tracked here as `UP-020`,
  `UP-021`, `UP-023`, `UP-024`, `UP-026`.
- **A green unrelated harness (`./scripts/sv0 test`) is not conformance
  evidence** for this package (SPEC principle 10).

## Authority order (SPEC §3.3), for disputes

1. `sv0doc` for language / type / ownership / contract semantics
2. the licensed final C or POSIX standard for compatibility behavior
3. accepted sv0 semantic decisions and milestone completion criteria
4. `sv0c` / `sv0vm` observable behavior for current implementation status
5. `sv0-toolchain` command and test contracts
6. this package's safe-native design decisions (SPEC)
7. examples and informative guidance

A discrepancy is recorded as a capability gap, resolved upstream, and
regression-tested — never silently resolved in the library.
