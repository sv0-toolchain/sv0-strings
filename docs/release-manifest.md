# Immutable, content-addressed release manifest (SS-190 / BL-098 / BACKEND-007 / GOV-002)

Generated by `scripts/release_manifest` (a CI step; regenerated on every
run — the toolchain revisions are optional to capture, no build required)
and gated by `tools/check_release_manifest.py` (in `scripts/check`,
dependency-free).

**Verdict: every catalog digest self-consistent with its live file; the
manifest-digest verified against the recorded body; every CI run's
manifest is uploaded as a build artifact.**

## Schema — `tools/catalogs/release_manifest.tsv`

`component` / `value`, one row per field:

| component | meaning |
|---|---|
| `sv0-strings-head` | this repo's commit SHA at generation time |
| `sv0-toolchain-head` | the parent `sv0-toolchain` checkout's commit SHA (`unknown` if not discoverable) |
| `sv0c-head` / `sv0vm-head` | the toolchain's own submodule SHAs |
| `cc-version` | the host C compiler's version string |
| `supported-targets` | the comma-joined `target` column of `tools/catalogs/targets.tsv` |
| `catalog-digest:<name>` | SHA-256 of `tools/catalogs/<name>`, one row per catalog file (except the manifest itself) |
| `manifest-digest` | SHA-256 over every row above it (always the **last** row) — the content address for this snapshot |

## What "content-addressed" means here

`manifest-digest` is computed over the exact bytes of every row above it
(component + tab + value, `\n`-joined, no catalog file's *content* omitted
— only its digest is recorded, not the file itself, keeping the manifest
small). Two manifests with identical `manifest-digest` values are
guaranteed to have identical toolchain revisions, compiler version,
supported-target list, and every evidence catalog's content — the digest
**is** the release's identity for auditing purposes (GOV-002: "current-
state claims SHALL cite exact audited revisions").

## What is and isn't a drift gate

Unlike `scripts/contract_matrix` / `scripts/consumer_rehearsal`, this
manifest's `*-head` revision fields are **expected** to change on every
commit — they document "true as of generation time", like a lockfile, not
an invariant. What `check_release_manifest.py` gates on every commit,
without needing the toolchain, is **self-consistency**:

* every `catalog-digest:<name>` row equals the live SHA-256 of
  `tools/catalogs/<name>` — an evidence catalog edited without
  regenerating the manifest is caught immediately (staleness / tamper);
* `manifest-digest` equals SHA-256 of the exact body above it — catches a
  hand-edit to the manifest file itself.

## Archival

Every CI run uploads `tools/catalogs/release_manifest.tsv` as the
`release-manifest` build artifact (`if: always()`, so even a failing run
leaves a record). The manifest checked into the repository at any given
commit is the snapshot as of that commit; SS-192 (approve + tag R1) will
regenerate it one final time at the tag commit as the archived release
record.
